# SchrauberOS – Hinweise für Claude

Werkstatt-Dashboard (Next.js 16, App Router, Prisma 7, SQLite – eine Datei, im Container unter /data). Sprache der UI und Doku: Deutsch (Standard) + Englisch.
Architektur, Befehle und das Rezept für neue Features stehen in `README.md` – bitte dort nachlesen statt hier zu duplizieren.

@AGENTS.md

## Regeln, die man nicht aus dem Code ablesen kann

* **Next.js ist hier nicht das, was du kennst** (siehe AGENTS.md): `middleware` heißt `proxy.ts`, `params`/`searchParams`/`cookies()` sind Promises. Doku liegt in `node_modules/next/dist/docs/`. `cacheComponents` ist bewusst **aus** (komplett eingeloggte, dynamische App).
* **Jede Seite und jede Server Action prüft selbst** (`requirePermission`/`requireSession`). `proxy.ts` und das Ausblenden in der Navigation sind nur Komfort, kein Schutz.
* **Eine Datenbank:** SQLite (eine Datei, im Container unter `/data`), Schema nur in `prisma/schema.prisma`. Keine Enums/Json-Felder (hält einen späteren Wechsel offen); Zustandswerte sind Strings aus `src/lib/domain/constants.ts`. Für Textsuche immer `contains()` aus `src/server/search.ts`.
* **Migrationen:** Es gibt genau **eine** Baseline `00000000000000_baseline` (erste Zeile: Marker `-- schrauberos:baseline unreleased|frozen`). **Solange `unreleased` (bis zur Veröffentlichung von v0.2.0):** Schema-Änderung → `schema.prisma` ändern, `npm run db:baseline` (erzeugt die Baseline neu und ersetzt alle Migrationsordner), `npm run db:fresh`; keine einzelnen Migrationen, keine Rückwärtskompatibilität zu 0.1.0 (fremde Migrationshistorie → die App startet nicht: „Neuinstallation nötig"). **Ab `frozen` (Veröffentlichung, gesetzt von `npm run db:freeze`: Marker `frozen sha256:…` + `prisma/published-migrations.json`; `npm test` und die Pipeline bei Versions-Tags prüfen die Prüfsummen, `npm run db:release-check` vergleicht mit dem letzten Release-Tag):** die Baseline und alle veröffentlichten Migrationen nie ändern (Web-Updates und bestehende Installationen hängen daran), nur additiv und zum Code der Vorversion kompatibel (Rückfall beim Web-Update); Schema-Änderung → `npm run db:migrate -- <name>`. Der Wächter `src/lib/migration-guard.ts` prüft das (kein DROP/RENAME, kein NOT NULL ohne Default, kein neuer Unique auf Bestandstabellen, DELETE/UPDATE, Trigger und PRAGMA nur mit begründetem Marker `-- guard:allow <regel>: <Begründung>`); `npm run db:check` (Drift Schema ↔ Migrationen) läuft lokal und in der Pipeline.
* **Betriebskonzept: einmal aufsetzen, danach alles über die Weboberfläche** (Backups, Wiederherstellung, Updates, Einstellungen) – neue Betriebsaufgaben nie als Umgebungsvariable/Kommando am Server lösen, sondern als Funktion in der App. Ein Container, ein Volume `/data` (Datenbank, `backups/`, `app/versions/`, `restore/`, `secret.key`). **Off-Site-Backup** (SFTP/WebDAV, Verwaltung → Backups → Off-Site): Dateien nur verschlüsselt (`.sobk`, `src/lib/offsite/crypto.ts`) und nur mit eigenem Namensmuster löschen; SFTP-Hostschlüssel fest hinterlegt (Abbruch vor der Anmeldung bei Abweichung), WebDAV nur HTTPS ohne Weiterleitungen; neue Abhängigkeit `ssh2` ohne native Teile (`allowScripts` verneint).
* **Hintergrundarbeit läuft über den Job-Runner** (`src/server/jobs`, README „Job-Runner“): Funktionen melden Jobs und Outbox-Abnehmer in ihrer `jobs.ts` an (eingetragen in `src/modules/jobs.ts`), nie eigene `setInterval`/Zeitgeber. Jobs sind wiederholbar (Neustart mitten im Lauf holt sie nach), werfen bei Fehlern (der Runner wiederholt mit Wartezeit und zeigt den Fehler im Systemstatus) und laufen nur, solange ihre Funktion aktiv ist. Outbox-Abnehmer sind über `message.id` idempotent.
* **Uploads und Archive:** Jede hochgeladene Datei geht durch `checkUpload` (`src/lib/upload-sniff.ts`, Inhalt statt gemeldetem Typ; gespeichert wird der erkannte Typ), wird nur über `deliveryHeaders` (`src/lib/file-delivery.ts`) ausgeliefert, und Upload-Routen prüfen `isSameOriginUpload` (`src/server/request-guard.ts`). Archive entpackt nur `extractArchive` (`src/lib/archive.ts`: keine Links/Geräte/`..`/absoluten Pfade, Grenzen für Einträge und Größe) – nie `tar.x` direkt. Dateizugriffe auf große Bäume (`/data/files`) asynchron, nie `*Sync` in Schleifen.
* **Update-Abruf nur über `fetchWithPolicy`** (`src/lib/updates/safe-fetch.ts`): Das Token geht nur an die API-Herkunft, Weiterleitungen nur auf die Allowlist der GitHub-Content-Server und nie mit `Authorization` – kein direktes `fetch` mit Token.
* **Backup-Aufbewahrung je Art** ist einstellbar (`src/server/backup/settings.ts`); das neueste Backup überhaupt wird nie gelöscht, fehlgeschlagene automatische Backups bleiben sichtbar (Backup-Seite, Dashboard, Systemstatus), bis eines gelingt.
* **Image = Starter + eingebaute App** (`FROM scratch`): `docker/bootstrap.c` (+ Prüfer `docker/verify.c` + vendortes Monocypher 4.0.3 in `docker/vendor/`, Prüfsummen-Test `vendor-monocypher.test.ts`, nie ändern; als `static-pie` mit `-Werror`; **nicht mehr winzig**: Spezifikation und Umsetzung in README „Starter-Vertrauensanker“) wählt per Zeiger `/data/app/active` das Verzeichnis, **prüft eine installierte Version bei jedem (Neu-)Start vollständig** (Siegel `SOS-SEAL`, Dateiliste `SOS-TREE`, Mengengleichheit ohne Ignorierbereich; die eingebaute App ist die Vertrauensbasis) und startet dessen Launcher. **Jedes Paket bringt alles mit**: Anwendung samt `node_modules`, Node, glibc/libstdc++/nss samt Lader (`runtime/`, gestartet über `runtime/<lader> --library-path …`) und den Launcher (`src/launcher/main.ts`, mit esbuild zu `launcher.mjs`). Kein System-`tar`, keine Shell, keine Prisma-CLI: Archive über die npm-Bibliothek `tar`. Die **App migriert sich selbst** (`src/instrumentation.ts` → `src/server/startup.ts`, Läufer `src/server/migrate.ts`); `/api/health` erst nach dem Start „ok“. Versionen/Rückfall/Restore: `src/lib/updates` (getestet); `writeState` schreibt auch den Aktiv-Zeiger. Release = Git-Tag `vX.Y.Z` (muss zu `package.json` passen), die Pipeline signiert Manifest und Siegel. `docker/BASE_VERSION` nur erhöhen, wenn sich der Vertrag des Starters ändert (Zeiger-Format, Exit-Codes, Aufruf der Laufzeit, Pflichtdateien im Paket). **Marker und Zustandsdateien unter `/data/app` sind Daten der App (uid 1000)**: Starter (`write_marker`) und Launcher der eingebauten Version (`removeMarker`, `writeState`) dürfen daran nie scheitern – auch nicht an einem Verzeichnis unter dem Namen einer Datei.
* **Das Paketverzeichnis ist zur Laufzeit read-only und vollständig geprüft:** nie in `process.cwd()` oder ins Paket schreiben (nur `/data` und `/tmp`; `images.unoptimized` und `isrFlushToDisk: false` in `next.config.ts` sind Pflicht — `/_next/image` ist unauthentifiziert erreichbar); **keine `node_modules` in Vorfahrenordnern** einer Version (`versions/`, `app/`, `DATA_DIR`: Node löste dort ungeprüften Code auf, Prüfcode 18); **Neustart der App immer über den Starter** — der Launcher startet die App je `run()` genau einmal, jeder Neustartpfad gibt `RESTART_EXIT_CODE` zurück (nie ein `continue`/interner Neustart); installierte Bäume werden nach der Prüfung schreibgeschützt, gelöscht wird nur über `removeTreeSync` (`lib/updates/fs-tree.ts`). Neue Dateiarten im Paket entstehen nur durch das Zusammenstellen von `/bundle` im Dockerfile (dort läuft `scripts/gen-tree.mjs`); der Generator bricht bei Sonderdateien, Setid, unzulässigen Namen und Links aus dem Baum laut ab. Prüfergebnisse haben drei Klassen (ok / negativ = Integritätsbefund → sperren / unklar = Betriebsfehler → nie sperren) plus „veraltet“ (Code 19, ohne Alarm); Rückfall zuerst auf die Vorversion, dann die eingebaute Version, mit Kompatibilitätsschranke gegen zu alten Code (`lib/updates/compat.ts`). Die Formate und Codes ändern nur gemeinsam mit `cases.json` (Goldkorpus: `npm run anchor:corpus`) **und** dem C-Prüfer: Wer `seal.ts`/`tree.ts`/`keychain.ts` oder den Korpus ändert, ändert `docker/verify.c` mit und lässt `npm run native:test` laufen (Linux/WSL mit gcc/clang; Stufen `corpus`, `mutation`, `parser` vergleichen C und Referenzprüfer Fall für Fall). Der Prüfer ist Sicherheitsgrenze: nur `openat`/`fstatat` relativ zu einem Verzeichnis-fd, authenticate-then-parse, längenbegrenzte Dezimalleser, nichts aus dem Baum vor der Signaturprüfung; Test-Konstanten (`SOS_BUILTIN_DIR`, `SOS_FUZZ_NO_SIGNATURE` …) nie in einem Produktions-Build (`-DSOS_PRODUCTION`).
* **Rechte-Hierarchie:** Wer Benutzer oder Rollen ändert, darf nie mehr Rechte erzeugen, als er selbst hat (Rohrechte, `src/lib/rbac.ts`; Prüfen+Schreiben in einer Transaktion). Rechte der Verwaltung stehen in der `feature.ts` unter `permissions.adminOnly` – nur Administratoren vergeben sie, Standardrollen enthalten sie nie. Neue Verwaltungsaktionen, die Rechte oder Rollen berühren, gehen durch diese Prüfung.
* **Anmeldung:** Passwörter nur mit scrypt über `src/server/auth/password.ts`: Anmeldungen höchstens 2 gleichzeitig (`hashSemaphore`, begrenzte Warteschlange), alles andere (Passwort setzen, Passwortabfrage im Konto, Notzugang, Anmeldung vom bekannten Gerät) auf dem **Eigentümer-Pfad** `ownerLane` (`FairLane`: je Konto/Vorgang höchstens eine laufende und eine wartende Berechnung, Warteschlange begrenzt und reihum; `hashPassword(pw, owner)` verlangt den Schlüssel, `QueueFullError` = `busy`) – nie hinter einer Flut von Anmeldungen. Unbekannte Namen **rechnen keinen Hash** (Timer-Auffüllung). Jede neue Eingabe, die ein Passwort prüft, braucht ein eigenes Limit (`loginThrottle`); Rücksprungziele nur über `safeNext`; Sitzungs- und Geräte-Cookie nur über `src/lib/session-cookie.ts` (unter HTTPS ausschließlich `__Host-…` lesen, zum Löschen `Secure`+Pfad `/` mitsenden). Das **bekannte Gerät** (`devices.ts`) gibt es nur auf Wunsch („Dieses Gerät merken“), befreit nur von der Konto-Wartezeit, **nie vom Passwort und nie vom zweiten Faktor**, verdrängt nie ein benutztes Gerät, zählt Fehlversuche auch in der Datenbank und wird in einer Transaktion gemerkt (ein Fehler dort darf die Anmeldung nie scheitern lassen); Anmeldezähler am Konto schreiben ohne `updatedAt` zu ändern (`updateLoginState`).
* **Zwei-Faktor-Anmeldung** (TOTP, optional; `second-factor.ts`, `pending.ts`): Geheimnis nur verschlüsselt (`encryptSecret`) und im Klartext nur in der Antwort der Einrichtung, Sicherungscodes nur als Hash; **keine Sitzung vor dem zweiten Schritt** (Zwischenzustand nur im Speicher des Servers), jeder Zeitschritt gilt einmal (bedingtes Update), eigenes Limit (`loginThrottle.totp`, dauerhaft in `TwoFactor`), die Prüfung ist billig und läuft nie über die scrypt-Pfade. Alles, was den Schutz senkt (einrichten, ausschalten, Codes erneuern, fremdes Konto zurücksetzen), verlangt die Passwortabfrage der handelnden Person (`confirmOwnPassword`). Notzugang, Administration und Restore ohne `secret.key` setzen den zweiten Faktor zurück (`resetSecondFactor`) und zeigen es dem Konto. Konto-/Sicherheitsoperationen sind `authenticated`-Operationen und nie API-Ressourcen.
* **Einrichtungs-Token** (`src/server/setup-token.ts`): Die Ersteinrichtung verlangt ein Token aus dem Container-Log (Datei `/data/setup-token`, 0600, nicht im Backup). Das ist die bewusste Ausnahme vom Betriebskonzept: einmalige Installationshandlung, kein laufender Betrieb. In Aktionen gilt: erst prüfen, ob schon ein Benutzer existiert, `applyTimezone` erst nach dem erfolgreichen Speichern (vorher `isValidTimezone`).
* **Notzugang** (`src/server/auth/recovery.ts`): Wiederherstellungs-Code nur als SHA-256-Hash, Klartext nur in der Antwort einer Action (nie URL/Log/Audit). Das Einlösen hat einen **eigenen Pfad** (nicht die scrypt-Semaphore), Drosselung nur global (nie pro Konto), identische Meldung und Dauer für alle Fehler. Alles, was einen Code erzeugt oder ersetzt, tut das in einer Transaktion über `replaceRecoveryCode`; Erzeugen im Konto nur für Administratoren mit Passwortabfrage.
* **Release-Signaturen** laufen über eine Schlüsselkette (`src/lib/updates/keychain.ts`, `release-key.ts`): Wurzelschlüssel (privat offline) beglaubigt Release-Schlüssel (Beglaubigung Format 2, 118 Bytes, Pflicht-Ablauf ≤ 5 Jahre), der Manifest (Kontext `schrauberos-manifest-v1`) und Siegel (`SOS-SEAL`, Beglaubigung eingebettet) signiert; der Starter prüft den Ablauf der Beglaubigung nie, die App beim Installieren. Die Schlüssel kommen **nur aus `release-key.ts`** (Build): keine Umgebungsvariable überschreibt sie, Tests nutzen `setTrustAnchorsForTest`; Testschlüssel (`src/lib/updates/testdata/anchor/test-keys.ts`) nie in einem Tag-Build (`gen-trust-header.mjs` bricht ab). Private Schlüssel nie ins Repository; den Release-Schlüssel nie ohne Auftrag ändern. `latest`/`X.Y.Z` setzt erst der Job `release` nach der Echtprobe (Retag); Proben per `workflow_dispatch` nie mit dem Produktionsschlüssel. Abläufe: README, Abschnitte „Starter-Vertrauensanker“ und „Release und Signaturschlüssel“.
* **Datenaustausch (CSV)** (`src/server/csv`, `src/modules/exchange.ts`, README „Datenaustausch (CSV)“): Export und Import je Datenart mit **eigenen Rechten** (`<funktion>.export`/`.import`, im Katalog unter `permissions.marked` gekennzeichnet, **nie in Standardrollen und nie in einem API-Token**); sie sind keine API-Ressourcen. Der Import legt nur neu an (Dubletten überspringen, nie ändern), in **einer** Transaktion, mit Vorschau und Prüfsumme; Prüfung und Datensatz kommen aus den Operationen der Funktion (nicht doppelt bauen). Texte, die der Nutzer erfasst hat, gehen nur über `csvField` raus (Formelschutz `= + - @`); vom Programm erzeugte Zahlen als `Raw`/`moneyCell`. Neue Datenart: Rezept im README.
* **Tests:** Aktionen/Seiten werden mit dem Harness `src/test/harness.ts` gegen eine echte temporäre SQLite getestet (Beispiele siehe README, Abschnitt Tests); der zu testende Code wird nach `createTestEnv()` per `await import()` geladen. Komponenten werden wirklich gerendert (`src/test/dom.ts`, happy-dom + react-dom/client), nicht per Quelltext-Muster geprüft. `generateMetadata` liest Titel aus der Datenbank nur nach `sessionIfAllowed("<recht>")`.
* **Gleichzeitiges Bearbeiten:** Bearbeiten-Formulare tragen `version` (`versionOf(row)` aus `src/lib/concurrency.ts`) mit; Speichern-Operationen belegen die Zeile mit `claimRow(tx.modell, id, version)` **in der Transaktion** und melden sonst `fail("conflict")` (`common.conflict`). Prüfen+Schreiben, die zusammengehören, laufen im Aktions-Rahmen in einer Transaktion. Neue Bearbeiten-Formulare müssen das übernehmen (nur Tabellen mit `updatedAt`).
* **Aktions-Rahmen** (`src/server/operations`, Details README „Aktionen und Operationen“): **Jede Server Action** ist `defineAction(defineOperation({ name, permission, input, audit, run }))` – `permission` Pflicht ohne Standard, `audit: "<aktion>"` oder `audit: false` + `auditReason`. `run` ist transportneutral: **kein** `redirect`/`next/*`/Flash/Übersetzung, Fachfehler über `fail()`/`failField()` mit Meldungsschlüsseln, Schreibzugriffe **nur über `ctx.tx`** (nie `db` in der Transaktion), Aufwendiges in `prepare`. Aktionen ohne Formularzustand melden per Flash (nur Meldungsschlüssel). Ereignisse für Webhooks nur über `ctx.emit` (Outbox, gleiche Transaktion); Hooks anderer Funktionen über `operation-hooks`. Log-Hygiene: nur Fehlercodes (`src/lib/log-safe.ts`), nie Meldungen/Stack/Nutzdaten. `architecture.test.ts` erzwingt den Rahmen (Liste der Altlasten darf nur schrumpfen), `matrix.test.ts` prüft jede Action/Route ohne Sitzung, mit `mustChangePassword` und falschem Recht.
* **API (`/api/v1`, Details: `README.md`, Abschnitt „Programmierschnittstelle“):** Jede fachliche Funktion bringt ihre Ressourcen in `api.ts` mit (`defineResource`, eingetragen in `src/modules/api.ts`); die Operationen liegen in `operations.ts` (ohne `"use server"`), `actions.ts` enthält nur `defineAction` – die API ruft **dieselben** Operationen (kein zweiter Schreibweg, Eingabeschemas getrennt). Jede schreibende UI-Aktion braucht ein API-Pendant **oder** einen begründeten Eintrag in `src/modules/api-exceptions.ts` (`api.test.ts` schlägt sonst fehl). Plattform/Verwaltung (Benutzer, Rollen, Einstellungen, Module, Backups, Updates, Audit, API selbst) ist nie API-Ressource; kein Token trägt `adminOnly`-/Verwaltungsrechte oder `employees.sensitive` (`isApiForbidden`), sensible Mitarbeiterdaten und Krankheit gibt es in der API nicht. Wirksame Rechte = Scope ∩ aktuelle Rechte des Besitzers, bei jeder Anfrage. Tokens nur als SHA-256-Hash, Klartext nur im Ergebnis der Erzeugung (nie Log/Audit/URL); Cookie und Token nie vermischen (die API liest nie das Sitzungs-Cookie, Seiten/Aktionen nie den `Authorization`-Header). Drosselung nur im Fehlerpfad ungültiger Tokens, nie vor dem Hash-Lookup. Neue Endpunkte: Struktur-Momentaufnahme `openapi-structure.txt` erneuern (`UPDATE_API_SNAPSHOT=1`).
* **Geheimnisse** (z. B. Update-Token, Off-Site-Zugangsdaten) nur über `setSecret/getSecret` (`src/server/settings.ts`, verschlüsselt, Schlüssel `secret.key` nicht in Backups). **Jedes neue Geheimnis meldet seinen Verbraucher an** (`secrets.ts` der Funktion → `src/modules/secrets.ts`, Typ `SecretConsumerDef`): Er setzt zurück, was nach einem Restore ohne passenden Schlüssel unlesbar ist (`src/server/secret-reset.ts`, Audit `secrets.reset`, Hinweis für Administratoren). Der **Wiederherstellungsschlüssel** (`src/server/recovery-key.ts`, Recht `backup.keys`, adminOnly, nur `isAdmin` mit Passwortabfrage) ist ein zufälliger 256-Bit-Schlüssel, nie gespeichert und nur in der Antwort der Aktion sichtbar (nie URL/Log/Audit); er umhüllt eine Kopie von `secret.key` in der Datenbank und leitet den Off-Site-Hauptschlüssel ab (**ein Schlüssel für alles**, keine Passphrase). Restore mit Schlüssel setzt `secret.key` im selben Launcher-Schritt wieder ein; seine Eingabe ist **global** gedrosselt (`loginThrottle.recoveryKey`, verlangsamt statt abzuweisen, nie pro Konto, eigener Pfad ohne scrypt-Semaphoren). Ein Restore in der Einrichtung (`/api/setup/restore`) verlangt das **Einrichtungs-Token**.
* **`secret.key` hat drei Zustände** (`readSecretKey`, `src/server/secrets.ts`): lesbar / fehlt / nicht lesbar. „Nicht lesbar“ oder „fehlt“ ist **nie** „fremder Schlüssel“: `decryptSecret` wirft dann `SecretKeyUnavailableError` (nur bei lesbarem Schlüssel und fehlschlagender GCM-Prüfung liefert es `null` = „gehört nicht zu mir“), ein neuer Schlüssel entsteht nur bei frischer Datenbank, die Anmeldung bleibt für Konten mit zweitem Faktor zu (fail-closed). **Zurückgesetzt wird nur über `resetUnreadableSecrets` (`secret-reset.ts`)**: nie im Anmeldepfad, nur bei lesbarem Schlüssel, bei fremdem Volume mit Hülle nur nach ausdrücklicher Wiederherstellung oder auf Anweisung der Administration, und immer erst nach Sicherung der Zeilen (`<DATA_DIR>/secret-reset/`). Der Weg zurück ohne Datenverlust: Wiederherstellungsschlüssel → `/login/key` bzw. Verwaltung → Backups → Schlüssel.
* **Übersetzungen:** `src/i18n/messages/de.ts` definiert die Struktur, `en.ts` muss identisch sein (Typfehler sonst). Größere Module haben eigene Dateien `messages/modules/<modul>.de.ts` / `.en.ts` (`en` ist als `typeof de` typisiert), die in de.ts/en.ts eingebunden werden. Dynamische Schlüssel (Enum-Werte) über `td(key, fallback)`; Plural über `<key>_one` / `<key>_other` und `tp()`.
* **Dokumentation hat zwei Orte:** `README.md` = Entwicklerdokumentation (Architektur, Betrieb, Release, Signaturschlüssel – dort pflegen, wenn sich etwas Technisches ändert). `docs/` = Anwendungsdokumentation für die Nutzer, in der App unter **Hilfe** (`/help`, Plattform, für alle angemeldeten Benutzer, kein Recht nötig; `src/platform/help`). Dort steht nur, was man **in der App** tut – keine Docker-/Entwickler-Themen. Die Hilfe ist **nach Modulen gegliedert und gehört den Funktionen**: Kapitel einer Funktion liegen in `docs/<modul>/<funktion>.md` und werden von der Funktion in `help.ts` (`HelpTopicDef`) angemeldet, gesammelt in `src/modules/help.ts` – sie verschwinden mit der Funktion (Aktivierung + Recht). Allgemeines liegt in `docs/platform/NN-name.md`. Ändert sich Bedienung/Verhalten, das passende Kapitel mitpflegen; neue Funktion = neues Kapitel samt `help.ts`.
* **Verwaltung ist Plattform:** Das Modul `admin` und alle seine Funktionen sind `required: true` (Benutzer, Rollen, Einstellungen, Module, Backups, Updates, Audit-Log) und nie abschaltbar; neue Verwaltungsfunktionen ebenfalls als `required`. Die Seite „Module & Funktionen“ zeigt nur fachliche Module.
* **Standard „aus“:** `defineFeature`/`defineModule` kennen `defaultEnabled` (Vorgabe true = Bestand). **Neue Funktionen setzen `defaultEnabled: false`**; eingeschaltet wird über „Module & Funktionen“ bzw. später Presets. Logik `catalog-logic.ts`.
* **Module und Funktionen** (Details: `README.md`): `src/modules/<modul>/<funktion>/` mit `feature.ts` (`defineFeature`), eingetragen in `src/modules/catalog.ts`. Der Katalog erzeugt Rechte-Typen, Navigation, Aktivierung (Admin-Seite „Module & Funktionen“), Rollen-Maske. Ausgeschaltete Funktion = keine Rechte in der Session = 404/ausgeblendet; Daten bleiben.
* **Funktionen reden nur über `public.ts` miteinander** und nur mit deklariertem `requires` (hart) bzw. `uses` (weich, zur Laufzeit mit `session.features.has(...)` prüfen). Plattform (`server`, `components`, `i18n`, `lib`, `platform`, `capabilities`) importiert keine Funktion. `src/architecture.test.ts` und `src/modules/catalog.test.ts` erzwingen das.
* **Einstellungen und Texte gehören der Funktion** (`settings-tab.tsx` → `settingsTabs`, `widgets.tsx` → `widgets`, beides in `src/modules/registry.ts` eingesammelt; Texte in `src/i18n/messages/modules/<funktion>.de.ts/.en.ts`). Standardrollen: `src/modules/default-roles.ts`.
* **Beiträge der Funktion statt zentraler Listen:** Audit-Aktionen (`auditActions` in der `feature.ts`; Plattform: `PLATFORM_AUDIT_ACTIONS` in `src/lib/audit-actions.ts`), Start-/Demo-Daten (`seed.ts`, eingesammelt in `src/modules/seed.ts`; Demo-Seed muss jede `[id]`-Seite der `pages.ts` bedienen, `seed.test.ts`), Route Handler unter `api/` über `routes` der `feature.ts`. Seeds importieren nichts mit `server-only` und finden fremde Daten über natürliche Schlüssel.
* **Datenzugriff über `queries.ts`:** Seiten, Bausteine, Suche und API lesen sensible Daten nur über die `queries.ts` der Funktion – explizites `select`, `viewer` als Parameter, sensible Spalten nur mit Recht **gar nicht erst aus der Datenbank gelesen** (nicht nachträglich maskieren). Keine `include: { customer: true }`-Voll-Relationen (`customerNameSelect`, `customerContacts`); Mitarbeiter-Tabellen nie roh in Seiten/Bausteinen (Architekturtest).
* **Zeit nur in der Werkstatt-Zone:** Tage/Uhrzeiten/Wochen/Monate über `src/lib/zone.ts` bzw. `lib/dates.ts` (`workshopZone()` aus der Einstellung), nie `process.env.TZ`, `date-fns`, `getHours()`/`setDate()` oder `new Date(2026, 0, 1)`/`new Date("…T12:00:00")` (Architekturtest „Zeitzone“). Kalendertage speichert `noon(day)` (12:00 der Werkstatt-Zone), Tests mit `withWorkshopZone(zone, fn)` (Prozess läuft in anderer Zone).
* **Audit-Log:** jede Operation des Rahmens nennt ihre Audit-Aktion (der Eintrag entsteht in der Transaktion der Änderung; `ctx.audit({ target, entityId })`); Aktionen stehen in `auditActions` der `feature.ts` (Plattform: `src/lib/audit-actions.ts`) und brauchen Beschriftungen `audit.actions.*`. Außerhalb des Rahmens (Anmeldung, Route Handler) `await audit("<aktion>", { target })` aus `@/server/audit`. Aufbewahrung: Standard 730 Tage (Scheduler, `src/server/audit-retention.ts`).
* **Geld** immer als ganze Cent (`Int`), Eingabe über `parseMoneyToCents`. **Dateien/Bilder** (Rechnungsbelege, Doku-Bilder) liegen als normale Dateien unter `/data/files` (`src/server/files.ts`: `storeFile/removeFile/moveFile`, lesbare ASCII-Pfade, nie überschreiben, nie verändern – Backups nutzen Hardlinks); die DB hält nur den relativen `path` (`InvoiceFile`, `DocImage`). Ausgeliefert nur über Route Handler mit Rechteprüfung. Nie Binärdaten in die DB.
* **Sensible Mitarbeiterdaten** (Notfallkontakt, Krankheit) nur mit `employees.sensitive` anzeigen/ändern; Krankheit wird sonst maskiert (`visibleAbsenceType`).
* **Fahrzeuge** (`Vehicle.customerId`) sind optional – Code darf nie `vehicle.customer.x` ohne Null-Prüfung nutzen; Anzeigenamen über `customerDisplayName()` (liefert „–“ bei null).
* **UI-Bausteine statt eigener Elemente:** Buttons, Felder, Tabellen, Karten, Menüs usw. kommen **ausschließlich** aus `src/components/ui` (`Button`, `LinkButton`, `Input`, `Select`, `Checkbox`, `Table`, `Card`, `FilterBar`, `Disclosure`, `Menu` …). Fehlt eine Variante, wird sie im Baustein ergänzt – nie lokal nachgebaut. Rohe `<button>/<input>/<select>/<textarea>/<table>/<label>/<details>` und die CSS-Klassen der Bausteine (`btn`, `input`, `card` …) sind außerhalb von `components/ui` verboten (`ui-kit.test.ts`). Nur Funktionen dürfen für einen echten Spezialfall ein eigenes Element mitbringen, mit Kommentar `ui-kit-exception: <Grund>` in der Datei.
* **Design:** nur Tokens aus `src/app/tokens.css` / Tailwind-Utilities (`bg-surface`, `text-ink-muted`, …), keine Rohfarben in Komponenten. Hell/Dunkel über `light-dark()`. **Touch:** Höhe von Bedienelementen und Eingabeschrift nur über `--tap`/`--tap-sm`/`--tap-chip`/`--tap-row`/`--input-font` (`tokens.css`: 36 px/14 px am Desktop, 44 px/16 px bei grobem Zeiger und unter 1024 px) – keine festen `min-h-8/9` in Bausteinen; eigene Links in Listen und Tabellen `min-h-(--tap-row) min-w-(--tap-row)`; Kennzeichen/FIN `autoCapitalize="characters" autoCorrect="off" spellCheck={false}`; `autoFocus` gilt nur am Desktop (`Input`).
* **Content-Security-Policy** (`src/lib/csp.ts`, Details README „Sicherheits-Header“): erzwungen, Nonce je Anfrage vom Proxy (Next liest ihn aus dem Kopf der *Anfrage*), `script-src` ohne `'unsafe-inline'`. **Genau eine Stelle setzt die CSP einer Antwort:** Proxy (Seiten/JSON), die Route selbst (Dateirouten, `ROUTE_OWNED_PATHS` – neue Route mit `deliveryHeaders` dort eintragen, der Test erzwingt es) oder `next.config` (nur Pfade außerhalb des Proxys); Next verwirft den Kopf einer Route still, wenn er schon gesetzt ist. Keine eigenen Inline-Skripte/`<style>` (sonst `nonce` aus `x-nonce`), kein `<object>`/`<embed>` (PDF per `PdfPreview`-`<iframe>`), kein `style-src`-Ausweichen außer `style-src-attr`. Notschalter „nur melden“ (Einstellungen → Sicherheit) liegt im Prozess (`lib/csp-mode.ts`), nicht in der Datenbank-Abfrage des Proxys.
* **Server-only Code** (`server-only`-Import) darf nicht vom Seed-Skript (`prisma/seed.ts`) importiert werden – dafür gibt es `src/server/db-client.ts`.
* Kein `useEffect` mit synchronem `setState` (ESLint `react-hooks/set-state-in-effect`), keine `Date.now()`/`new Date()` direkt im Komponenten-Body (`react-hooks/purity`) – in Helfer auslagern.

* **Browser-CI** (`e2e/`, Playwright, nur Tests): Jede Funktion meldet ihre Seiten in `pages.ts` (`definePages`) und in `src/modules/pages.ts` (Routen-Inventur; `pages.test.ts` erzwingt es); der Demo-Seed muss jede Seite abdecken. Baseline-Listen bekannter Verstöße (`e2e/baselines/`) dürfen nur schrumpfen (neue Verstöße und erledigte Einträge brechen den Lauf); Screenshots nur in einem eigenen Commit „snapshots“. Der Job `e2e` läuft nicht bei jedem Push auf `main`.

## Prüfen vor dem Abschluss

`npm run typecheck && npm run lint && npm test` – und bei größeren Änderungen `npm run build`. Änderungen an `docker/` (Starter, Prüfer): zusätzlich `npm run native:test` (Linux oder WSL mit gcc/clang; `-- fuzz --fuzz-seconds 60` für die libFuzzer-Ziele; `-- l3` mit Docker).
