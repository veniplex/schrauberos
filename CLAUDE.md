Werkstatt-Dashboard (Next.js 16, App Router, Prisma 7, SQLite – eine Datei, im Container unter /data). Sprache der UI und Doku: Deutsch (Standard) + Englisch (die Hilfe `docs/` nur Deutsch).

## Regeln, die man nicht aus dem Code ablesen kann

### Grundlagen

* **Next.js ist hier nicht das, was du kennst** (siehe AGENTS.md): `middleware` heißt `proxy.ts`, `params`/`searchParams`/`cookies()` sind Promises. Doku liegt in `node_modules/next/dist/docs/`. `cacheComponents` ist bewusst **aus** (komplett eingeloggte, dynamische App).
* **Jede Seite und jede Server Action prüft selbst** (`requirePermission`/`requireSession`). `proxy.ts` und das Ausblenden in der Navigation sind nur Komfort, kein Schutz.
* **Eine Datenbank:** SQLite (eine Datei, im Container unter `/data`), Schema nur in `prisma/schema.prisma`. Keine Enums/Json-Felder (hält einen späteren Wechsel offen); Zustandswerte sind Strings aus der `constants.ts` der jeweiligen Funktion (zum Beispiel `src/modules/workshop/orders/constants.ts`). Textsuche immer über `contains()`/`searchWhere` aus `src/server/search.ts`; **Namen, Orte, Telefon, Kennzeichen und Rechnungspartner** suchen über Schlüsselspalten (`Customer.nameKey/cityKey/phoneKey`, `Vehicle.searchKey`, `Invoice.partyKey`, `search-key.ts`, `keyContains`): jeder Schreibweg (`customerRecord/vehicleRecord/invoiceRecord`) setzt sie, Tests mit Direktanlage tragen sie selbst ein.
* **Migrationen:** Es gibt genau **eine** Baseline `00000000000000_baseline` (erste Zeile: Marker `-- schrauberos:baseline unreleased|frozen`). **Solange `unreleased` (bis zur Veröffentlichung von v0.2.0):** Schema-Änderung → `schema.prisma` ändern, `npm run db:baseline` (erzeugt die Baseline neu und ersetzt alle Migrationsordner), `npm run db:fresh`; keine einzelnen Migrationen, keine Rückwärtskompatibilität zu 0.1.0 (fremde Migrationshistorie → die App startet nicht: „Neuinstallation nötig“). **`npm run db:freeze` läuft erst unmittelbar vor dem Tag und nur auf Anweisung des Nutzers** (Marker `frozen sha256:…` + `prisma/published-migrations.json`; `npm test` und die Pipeline bei Versions-Tags prüfen die Prüfsummen, `npm run db:release-check` vergleicht mit dem letzten Release-Tag). **Ab `frozen`:** die Baseline und alle veröffentlichten Migrationen nie ändern (Web-Updates und bestehende Installationen hängen daran), nur additiv und zum Code der Vorversion kompatibel (Rückfall beim Web-Update); Schema-Änderung → `npm run db:migrate -- <name>`. Der Wächter `src/lib/migration-guard.ts` prüft das (kein DROP/RENAME, kein NOT NULL ohne Default, kein neuer Unique auf Bestandstabellen, DELETE/UPDATE, Trigger und PRAGMA nur mit begründetem Marker `-- guard:allow <regel>: <Begründung>`); `npm run db:check` (Drift Schema ↔ Migrationen) läuft lokal und in der Pipeline.
* **Betriebskonzept: einmal aufsetzen, danach alles über die Weboberfläche** (Backups, Wiederherstellung, Updates, Einstellungen) – neue Betriebsaufgaben nie als Umgebungsvariable/Kommando am Server lösen, sondern als Funktion in der App. Ein Container, ein Volume `/data` (Datenbank, `backups/`, `app/versions/`, `restore/`, `secret.key`). **Off-Site-Backup** (SFTP/WebDAV): Dateien nur verschlüsselt (`.sobk`, `src/lib/offsite/crypto.ts`) und nur mit eigenem Namensmuster löschen; SFTP-Hostschlüssel fest hinterlegt, WebDAV nur HTTPS ohne Weiterleitungen; `ssh2` ohne native Teile (`allowScripts` verneint).
* **Einrichtungs-Token** (`src/server/setup-token.ts`): Die Ersteinrichtung verlangt ein Token aus dem Container-Log (Datei `/data/setup-token`, 0600, nicht im Backup). Das ist die **bewusste Ausnahme vom Betriebskonzept: einmalige Installationshandlung, kein laufender Betrieb.** In Aktionen gilt: erst prüfen, ob schon ein Benutzer existiert, `applyTimezone` erst nach dem erfolgreichen Speichern (vorher `isValidTimezone`).
* **Hintergrundarbeit läuft über den Job-Runner** (`src/server/jobs`, README „Job-Runner“): Funktionen melden Jobs und Outbox-Abnehmer in ihrer `jobs.ts` an (eingetragen in `src/modules/jobs.ts`), nie eigene `setInterval`/Zeitgeber. Job-IDs `<bereich>.<name>` nur aus Kleinbuchstaben (Name auch Bindestrich; Test). Jobs sind wiederholbar (Neustart mitten im Lauf holt sie nach), werfen bei Fehlern (der Runner wiederholt mit Wartezeit und zeigt den Fehler im Systemstatus), melden nur Auffälliges (keine Meldung bei leerem Lauf) und laufen nur, solange ihre Funktion aktiv ist. Outbox-Abnehmer sind über `message.id` idempotent und beachten `signal`.
* **Uploads und Archive:** Jede hochgeladene Datei geht durch `checkUpload` (`src/lib/upload-sniff.ts`, Inhalt statt gemeldetem Typ; gespeichert wird der erkannte Typ), wird nur über `deliveryHeaders` (`src/lib/file-delivery.ts`) ausgeliefert, und Upload-Routen prüfen `isSameOriginUpload` (`src/server/request-guard.ts`). **Fotos** (nur JPEG/PNG; HEIC/WebP wandelt der Browser um, sonst abgelehnt) bereinigt `image-sanitize.ts` mit **Positivliste** (EXIF/GPS und alles Unbekannte fliegen raus), Obergrenzen vor dem Dekodieren, Kontingent je Konto über `ByteBudget`; entfernte Dateien löscht erst der Job `files.purge`. Archive entpackt nur `extractArchive` (`src/lib/archive.ts`) – nie `tar.x` direkt. Dateizugriffe auf große Bäume (`/data/files`) asynchron, nie `*Sync` in Schleifen.
* **Update-Abruf nur über `fetchWithPolicy`** (`src/lib/updates/safe-fetch.ts`): Das Token geht nur an die API-Herkunft, Weiterleitungen nur auf die Allowlist der GitHub-Content-Server und nie mit `Authorization` – kein direktes `fetch` mit Token.
* **Ausgehende Verbindungen** (Überwachung, Webhooks, Off-Site, Mail) prüfen **jede aufgelöste Adresse** (Loopback, Verbindungs-lokal, Metadaten, eigener Rechner, Docker-Host-Gateway – `lib/offsite/host-policy.ts`, `server/host-gateway.ts`) und verbinden zur geprüften IP (`resolvePinned`/Pinning; Name nur für SNI). `allowPrivate` öffnet private Netze, nie den Server selbst; keine neue Verbindungsart ohne diese Sperre. **Die Adresse der Anwendung** (QR-Codes, Abo-Adressen) kommt nur aus der Einstellung `app.publicUrl`, nie aus dem Host-Header.
* **Backup-Aufbewahrung je Art** ist einstellbar (`src/server/backup/settings.ts`); das neueste Backup überhaupt wird nie gelöscht, fehlgeschlagene automatische Backups bleiben sichtbar (Backup-Seite, Dashboard, Systemstatus), bis eines gelingt.

### Image, Starter, Release

* **Image = Starter + eingebaute App** (`FROM scratch`): `docker/bootstrap.c` (+ Prüfer `docker/verify.c` + vendortes Monocypher 4.0.3 in `docker/vendor/`, nie ändern; `static-pie`, `-Werror`; Spezifikation README „Starter-Vertrauensanker“) wählt per Zeiger `/data/app/active` das Verzeichnis, **prüft eine installierte Version bei jedem (Neu-)Start vollständig** (Siegel `SOS-SEAL`, Dateiliste `SOS-TREE`; die eingebaute App ist die Vertrauensbasis) und startet dessen Launcher. **Jedes Paket bringt alles mit** (App samt `node_modules`, Node, glibc/libstdc++/nss samt Lader, Launcher `src/launcher/main.ts`); kein System-`tar`, keine Shell, keine Prisma-CLI (Archive über die npm-Bibliothek `tar`). Die **App migriert sich selbst** (`src/instrumentation.ts` → `src/server/startup.ts`, Läufer `src/server/migrate.ts`); `/api/health` erst nach dem Start „ok“. Release = Git-Tag `vX.Y.Z` (muss zu `package.json` passen), die Pipeline signiert Manifest und Siegel. `docker/BASE_VERSION` nur erhöhen, wenn sich der Vertrag des Starters ändert. **Marker und Zustandsdateien unter `/data/app` sind Daten der App (uid 1000)**: Starter und Launcher der eingebauten Version dürfen daran nie scheitern – auch nicht an einem Verzeichnis unter dem Namen einer Datei.
* **Das Paketverzeichnis ist zur Laufzeit read-only und vollständig geprüft:** nie in `process.cwd()` oder ins Paket schreiben (nur `/data` und `/tmp`; `images.unoptimized` und `isrFlushToDisk: false` in `next.config.ts` sind Pflicht); **keine `node_modules` in Vorfahrenordnern** einer Version; **Neustart der App immer über den Starter** (jeder Neustartpfad gibt `RESTART_EXIT_CODE` zurück, nie ein internes `continue`); installierte Bäume werden nach der Prüfung schreibgeschützt, gelöscht wird nur über `removeTreeSync` (`lib/updates/fs-tree.ts`). Neue Dateiarten im Paket entstehen nur durch das Zusammenstellen von `/bundle` im Dockerfile. **Dynamische Dateizugriffe** (`path.join(dataDir(), …)`, `process.cwd()`) bekommen `/*turbopackIgnore: true*/`, sonst zieht Turbopack das ganze Projekt (`.data`, `.env`, Tests) in den Standalone-Build; `scripts/check-bundle.mjs` bricht den Image-Bau bei Fremdem ab, `.data` steht in `.dockerignore`. Prüfergebnisse haben drei Klassen (ok / negativ = Integritätsbefund → sperren / unklar = Betriebsfehler → nie sperren) plus „veraltet“. Die Formate und Codes ändern nur gemeinsam mit `cases.json` (Goldkorpus: `npm run anchor:corpus`) **und** dem C-Prüfer: Wer `seal.ts`/`tree.ts`/`keychain.ts` oder den Korpus ändert, ändert `docker/verify.c` mit und lässt `npm run native:test` laufen (Linux/WSL). Der Prüfer ist Sicherheitsgrenze (nur `openat`/`fstatat` relativ zu einem Verzeichnis-fd, authenticate-then-parse, längenbegrenzte Leser); Test-Konstanten nie in einem Produktions-Build (`-DSOS_PRODUCTION`). `parseEndorsements` (Starter-Format) nicht ändern.
* **Release-Signaturen** laufen über eine Schlüsselkette (`src/lib/updates/keychain.ts`, `release-key.ts`): Wurzelschlüssel (privat offline) beglaubigt Release-Schlüssel (Pflicht-Ablauf ≤ 5 Jahre), der Manifest und Siegel signiert. Die Schlüssel kommen **nur aus `release-key.ts`** (Build): keine Umgebungsvariable überschreibt sie, Tests nutzen `setTrustAnchorsForTest`; Testschlüssel nie in einem Tag-Build. Private Schlüssel nie ins Repository; **Release-/Wurzelschlüssel, `db:freeze`, Tags und `git push` nie ohne Auftrag.** `latest`/`X.Y.Z` setzt erst der Job `release` nach der Echtprobe; Proben per `workflow_dispatch` nie mit dem Produktionsschlüssel. Abläufe: README „Release und Signaturschlüssel“.

### Sicherheit, Anmeldung, Geheimnisse

* **Rechte-Hierarchie:** Wer Benutzer oder Rollen ändert, darf nie mehr Rechte erzeugen, als er selbst hat (Rohrechte, `src/lib/rbac.ts`; Prüfen+Schreiben in einer Transaktion). Rechte der Verwaltung stehen unter `permissions.adminOnly` – nur Administratoren vergeben sie, Standardrollen enthalten sie nie. **Gekennzeichnete Rechte** (Regel 9, `permissions.marked`: `export/import/send/reveal/api/sensitive`) stehen nie in Standardrollen und Rollenvorlagen (`isRuleNinePermission`, `default-roles.ts`) und nie in einem API-Token (`API_NEVER`, `lib/api/scope.ts`); `permissions.explicitOnly` (IT-Tresor) gilt **nicht einmal für Administratoren**, nur über eine Rolle, die es ausdrücklich enthält (jede Vergabe im Audit). Neue Rechte brauchen `permissionHints.*`. Neue Verwaltungsaktionen, die Rechte oder Rollen berühren, gehen durch die Hierarchieprüfung.
* **Anmeldung:** Passwörter nur mit scrypt über `src/server/auth/password.ts`: Anmeldungen höchstens 2 gleichzeitig (`hashSemaphore`), alles andere (Passwort setzen, Passwortabfrage im Konto, Notzugang, Anmeldung vom bekannten Gerät) auf dem **Eigentümer-Pfad** `ownerLane` (`FairLane`; `hashPassword(pw, owner)`, `QueueFullError` = `busy`) – nie hinter einer Flut von Anmeldungen. Unbekannte Namen **rechnen keinen Hash**. Jede neue Eingabe, die ein Passwort prüft, braucht ein eigenes Limit (`loginThrottle`); Rücksprungziele nur über `safeNext`; Sitzungs- und Geräte-Cookie nur über `src/lib/session-cookie.ts` (unter HTTPS ausschließlich `__Host-…` lesen, zum Löschen `Secure`+Pfad `/` mitsenden). Das **bekannte Gerät** (`devices.ts`) gibt es nur auf Wunsch, befreit nur von der Konto-Wartezeit, **nie vom Passwort und nie vom zweiten Faktor**; Anmeldezähler am Konto schreiben ohne `updatedAt` zu ändern (`updateLoginState`).
* **Zwei-Faktor-Anmeldung** (TOTP, optional; `second-factor.ts`, `pending.ts`): Geheimnis nur verschlüsselt, Sicherungscodes nur als Hash; **keine Sitzung vor dem zweiten Schritt**, jeder Zeitschritt gilt einmal, eigenes Limit (`loginThrottle.totp`), nie über die scrypt-Pfade. Alles, was den Schutz senkt (einrichten, ausschalten, Codes erneuern, fremdes Konto zurücksetzen), verlangt die Passwortabfrage der handelnden Person (`confirmOwnPassword`). Notzugang, Administration und Restore ohne `secret.key` setzen den zweiten Faktor zurück (`resetSecondFactor`). Konto-/Sicherheitsoperationen sind `authenticated`-Operationen und nie API-Ressourcen.
* **Notzugang** (`src/server/auth/recovery.ts`): Wiederherstellungs-Code nur als SHA-256-Hash, Klartext nur in der Antwort einer Action (nie URL/Log/Audit). Das Einlösen hat einen **eigenen Pfad** (nicht die scrypt-Semaphore), Drosselung nur global (nie pro Konto), identische Meldung und Dauer für alle Fehler. Erzeugen/Ersetzen nur in einer Transaktion über `replaceRecoveryCode`; im Konto nur für Administratoren mit Passwortabfrage.
* **Geheimnisse** (Update-Token, Off-Site-Zugangsdaten, Mail-Passwort, Webhook-Geheimnisse, Tresor) nur über `setSecret/getSecret` (`src/server/settings.ts`, verschlüsselt, Schlüssel `secret.key` nicht in Backups). **Jedes neue Geheimnis meldet seinen Verbraucher an** (`secrets.ts` der Funktion → `src/modules/secrets.ts`, `SecretConsumerDef`): Er setzt zurück, was nach einem Restore ohne passenden Schlüssel unlesbar ist (`src/server/secret-reset.ts`, Audit `secrets.reset`); `affectedRows` sichert die Zeilen vorher, `holdings` macht Zugriffe auf den Tresor im Audit auffällig. Krypto nur über `lib/gcm.ts` (Tag 16 Byte, IV 12, kanonisches Base64). Der **Wiederherstellungsschlüssel** (`src/server/recovery-key.ts`, Recht `backup.keys`, adminOnly + `isAdmin`, Passwortabfrage) ist ein zufälliger 256-Bit-Schlüssel, nie gespeichert, nur in der Antwort sichtbar; er umhüllt eine Kopie von `secret.key` und leitet den Off-Site-Hauptschlüssel ab (**ein Schlüssel für alles**, keine Passphrase); seine Eingabe ist **global** gedrosselt (`loginThrottle.recoveryKey`). Ein Restore in der Einrichtung verlangt das Einrichtungs-Token. Nach **jeder** Wiederherstellung sind Webhooks aus und API-Tokens widerrufen.
* **`secret.key` hat drei Zustände** (`readSecretKey`): lesbar / fehlt / nicht lesbar. „Nicht lesbar“ oder „fehlt“ ist **nie** „fremder Schlüssel“: `decryptSecret` wirft dann `SecretKeyUnavailableError` (nur bei lesbarem Schlüssel und GCM-Fehler `null`), ein neuer Schlüssel entsteht nur bei frischer Datenbank, die Anmeldung bleibt für Konten mit zweitem Faktor zu (fail-closed). **Zurückgesetzt wird nur über `resetUnreadableSecrets`**: nie im Anmeldepfad, nur bei lesbarem Schlüssel, nur `unreadable` automatisch (`damaged`/`unsupported` nur melden), immer erst nach Sicherung der Zeilen (`<DATA_DIR>/secret-reset/`). Der Weg zurück: Wiederherstellungsschlüssel → `/login/key` bzw. Verwaltung → Backups → Schlüssel.
* **IT-Tresor** (`it/docs/vault*.ts`): Zugriff auf `VaultEntry` **nur dort** (Architekturtest, auch Roh-SQL); URL/Benutzer/Passwort/Notiz verschlüsselt (AAD = ID, Titel/Art/System, Revision), Klartext nur in der Antwort einer Action mit Passwortabfrage, eigenem Limit und `no-store`, nie in Verlauf/Suche/API/Webhook/CSV; Recht `explicitOnly`; Schreibweg gesperrt bei Schlüsselstörung. **Überwachung** (`server/monitor`, `lib/monitor`): Ziele nur mit eigenem Recht `network.monitor` (sensitive, nie in Token, Ziele nicht per API), nur TCP/HTTP mit Statuszeile (nie Antworttext), Messungen ändern `updatedAt` des Ziels nie, Gerätestatus nie erfunden („Status unbekannt“ ohne Messung).
* **API (`/api/v1`, Details README „Programmierschnittstelle“):** Jede fachliche Funktion bringt ihre Ressourcen in `api.ts` mit (`defineResource`, eingetragen in `src/modules/api.ts`); Operationen in `operations.ts` (ohne `"use server"`), `actions.ts` nur `defineAction` – die API ruft **dieselben** Operationen. Jede schreibende UI-Aktion braucht ein API-Pendant **oder** einen begründeten Eintrag in `src/modules/api-exceptions.ts`. Plattform/Verwaltung (Benutzer, Rollen, Einstellungen, Module, Backups, Updates, Audit, API selbst) ist nie API-Ressource; kein Token trägt `adminOnly`-/gekennzeichnete Rechte oder `employees.sensitive` (`isApiForbidden`, `API_NEVER`). Wirksame Rechte = Scope ∩ aktuelle Rechte des Besitzers, bei jeder Anfrage; Tokens nur als SHA-256-Hash, Klartext nur im Ergebnis der Erzeugung (Erzeugen mit Passwortabfrage); **Dienstkonten** (`authSource=service`) überleben Passwortwechsel/Notzugang des Erzeugers, normale Tokens nicht. Cookie und Token nie vermischen. Drosselung nur im Fehlerpfad ungültiger Tokens. Ressourcen mit Elternkennung im Body prüfen `parentVisible` (Art. 18); `DELETE` kennt `scope`. Neue Endpunkte: `openapi-structure.txt` erneuern (`UPDATE_API_SNAPSHOT=1`). **Webhooks:** Ereignisse nur über `webhookEvents` der `feature.ts`; **jede Funktion mit Ereignissen bringt `webhooks.ts` mit** (Prüfung je Ressource, ohne Eintrag = eingeschränkt = fail-closed); Nutzlast ohne Fachdaten, Zielsperre (siehe „Ausgehende Verbindungen“), Verwaltungsseiten unter `/admin/api` (nicht `/api`, wegen Proxy-CSP).
* **Datenschutz (Art. 18):** Wer Kunden zur Auswahl oder Suche anbietet, nutzt `searchableCustomerWhere`; eingeschränkte Kunden sind dort, in der API, in Exporten, in Feeds und in neuen Verknüpfungen ausgeschlossen. Für Objekte mit Kunde **oder** Halter gelten die zentralen Bedingungen aus `customers/public.ts` (`unrestrictedByCustomer/ByVehicle/…`, `unrestrictedOrder/Document`) – nie handgeschrieben; Fehlermeldungen und Hinweise nennen ohne `customers.view` keine Namen. Funktionen mit Kundendaten bringen eine `privacy.ts` (Auskunft, Frist) und ggf. einen Hook auf `customers.anonymize` mit (`OperationHookDef.always`, damit auch ausgeschaltete Funktionen bereinigt werden). Die Anonymisierung bleibt gesperrt, bis ein Administrator die Aufbewahrungsfristen bestätigt hat (Standardfristen sind Platzhalter, Steuerberater); `customers.disclose`/`customers.privacy` gehören in keine Standardrolle. **Audit-Zeilen werden nie verändert** (auch nicht bei der Anonymisierung; Namen aus früheren Fassungen bleiben bis zur Audit-Aufbewahrungsfrist): neue `audit({ target })` nennen Kunden und Mitarbeiter nie mit Namen, nur über `personRef` (`src/lib/audit-ref.ts`).
* **Content-Security-Policy** (`src/lib/csp.ts`, README „Sicherheits-Header“): erzwungen, Nonce je Anfrage vom Proxy, `script-src` ohne `'unsafe-inline'`. **Genau eine Stelle setzt die CSP einer Antwort:** Proxy (Seiten/JSON), die Route selbst (Dateirouten, `ROUTE_OWNED_PATHS` – neue Route mit `deliveryHeaders` dort eintragen) oder `next.config` (nur Pfade außerhalb des Proxys). Keine eigenen Inline-Skripte/`<style>` (sonst `nonce` aus `x-nonce`), kein `<object>`/`<embed>` (PDF per `PdfPreview`-`<iframe>`). Notschalter „nur melden“ liegt im Prozess (`lib/csp-mode.ts`).
* **Server-only Code** (`server-only`-Import) darf nicht vom Seed-Skript (`prisma/seed.ts`) importiert werden – dafür gibt es `src/server/db-client.ts`.

### Funktionen, Aktionen, Daten

* **Module und Funktionen** (Details: `README.md`): `src/modules/<modul>/<funktion>/` mit `feature.ts` (`defineFeature`), eingetragen in `src/modules/catalog.ts`. Der Katalog erzeugt Rechte-Typen, Navigation, Aktivierung, Rollen-Maske. Ausgeschaltete Funktion = keine Rechte in der Session = 404/ausgeblendet; Daten bleiben. **Neue Funktionen setzen `defaultEnabled: false`**; eingeschaltet wird über „Module & Funktionen“ bzw. Presets (`src/modules/presets.ts`, Einrichtung). Das Modul `admin` und alle seine Funktionen sind `required: true` und nie abschaltbar; neue Verwaltungsfunktionen ebenfalls.
* **Funktionen reden nur über `public.ts` (Server) bzw. `client.ts` (Browserbündel)** miteinander und nur mit deklariertem `requires` (hart) bzw. `uses` (weich, zur Laufzeit mit `session.features.has(...)` prüfen). **Client-Module („use client“) importieren nie Server-Code** (`public.ts` anderer Funktionen, `queries.ts`, `server/*`): sonst 500 im Dev und Bruch im Build – dafür `client.ts` oder ein `ReactNode` von der Seite (Architekturtest „Client-Bündel“). Plattform (`server`, `components`, `i18n`, `lib`, `platform`, `capabilities`) importiert keine Funktion. `architecture.test.ts` und `catalog.test.ts` erzwingen das.
* **Beiträge der Funktion statt zentraler Listen:** Einstellungen (`settings-tab.tsx`), Widgets (`widgets.tsx`: `titleKey` + `priority` Pflicht, `uses` optional), Einrichtungs-Punkte (`setup-checks.ts` → `setupChecks`), Schnellaktionen (`quickActions`, `kind: "open"` für Dialoge), Suche (`search.ts`), Audit-Aktionen (`auditActions`; Plattform: `src/lib/audit-actions.ts`), Start-/Demo-Daten (`seed.ts`; muss jede `[id]`-Seite der `pages.ts` bedienen; Seeds importieren nichts mit `server-only`), Hilfe (`help.ts`), Routen unter `api/` (`routes`), Webhooks (`webhooks.ts`), Datenschutz (`privacy.ts`), Abschnitte auf Seiten anderer Funktionen (`sections.tsx`: `SectionDef` mit `host` aus `SectionHost`; Anhänge am Druck über `PrintNoteDef`). Texte in `src/i18n/messages/modules/<funktion>.de.ts/.en.ts`. Standardrollen: `src/modules/default-roles.ts`. Die Übersicht ist ein flaches Raster nach `priority`, nicht nach Modulen.
* **Hooks** (`hooks.ts`, eingetragen in `src/modules/operation-hooks.ts`): reagieren auf Operationen anderer Funktionen, nur mit deklariertem `requires`/`uses`; **kein Laufzeit-Import von `@/server/operations` in `hooks.ts`** (Zirkel; Fehler aus `@/server/operations/errors`); `OrderChange` u. Ä. sind der Vertrag, nicht die Tabelle der anderen Funktion. Hooks laufen nur für aktive Funktionen – außer `always`.
* **Aktions-Rahmen** (`src/server/operations`, README „Aktionen und Operationen“): **Jede Server Action** ist `defineAction(defineOperation({ name, permission, input, audit, run }))` – `permission` Pflicht ohne Standard, `audit: "<aktion>"` oder `audit: false` + `auditReason`. `run` ist transportneutral: **kein** `redirect`/`next/*`/Flash/Übersetzung, Fachfehler über `fail()`/`failField()` mit Meldungsschlüsseln, Schreibzugriffe **nur über `ctx.tx`** (nie `db` in der Transaktion), Aufwendiges in `prepare`. Ereignisse für Webhooks nur über `ctx.emit` (Outbox, gleiche Transaktion); Erfolgsmeldungen nennen das Objekt (`message: { key, params }` bzw. Funktion mit `i18n`), nie nur „Gespeichert.“; Hooks über `operation-hooks`. Log-Hygiene: nur Fehlercodes (`src/lib/log-safe.ts`), nie Meldungen/Stack/Nutzdaten. `architecture.test.ts` erzwingt den Rahmen (Liste der Altlasten darf nur schrumpfen), `matrix.test.ts` prüft jede Action/Route ohne Sitzung, mit `mustChangePassword` und falschem Recht.
* **Gleichzeitiges Bearbeiten:** Bearbeiten-Formulare tragen `version` (`versionOf(row)` aus `src/lib/concurrency.ts`) mit; Speichern belegt die Zeile mit `claimRow(tx.modell, id, version)` **in der Transaktion** und meldet sonst `fail("conflict")`; API-Aktionen über `If-Match`/`ifMatch`. Rückrufe gesteuerter Formularfelder rechnen aus dem aktuellen Zustand (Funktionsupdate/`useReducer`). **Fokus:** laufende Absende-Knöpfe/Schalter/Checkboxen setzen `aria-disabled`/`aria-busy`, nie `disabled` (ein gesperrtes Feld verliert den Fokus); `FocusRescue` fängt entfernte Elemente nach Tastaturbedienung auf. Prüfen+Schreiben laufen in einer Transaktion.
* **Datenzugriff über `queries.ts`:** Seiten, Bausteine, Suche und API lesen sensible Daten nur über die `queries.ts` der Funktion – explizites `select`, `viewer` als Parameter, sensible Spalten (auch Preisspalten) nur mit Recht **gar nicht erst aus der Datenbank gelesen**. Keine `include: { customer: true }`-Voll-Relationen (`customerNameSelect`, `customerContacts`); Mitarbeiter-Tabellen nie roh in Seiten/Bausteinen. `generateMetadata` liest Titel nur nach `sessionIfAllowed("<recht>")`.
* **Zeit nur in der Werkstatt-Zone:** Tage/Uhrzeiten/Wochen/Monate über `src/lib/zone.ts` bzw. `lib/dates.ts` (`workshopZone()` aus der Einstellung), nie `process.env.TZ`, `getHours()`/`setDate()`, `new Date(2026, 0, 1)` oder `new Date("…T12:00:00")` (Architekturtest „Zeitzone“). Kalendertage speichert `noon(day)`. **Tests laufen in der CI in UTC:** Uhrzeiten der Werkstatt setzen die Zone ausdrücklich (`withWorkshopZone`/`setWorkshopZone`), nie die reale Uhr oder Prozess-Zone (`TZ=UTC npm test` prüft).
* **Zähler und Nummern:** Fortlaufende Nummern nur über die Zählertabelle (`nextCounterValue`; Belege `allocateDocumentNumber`, `server/invoice-numbering.ts`) in der Transaktion des Anlegens; Muster nur über `lib/invoice-number-format.ts`.
* **Rechnungen und Belege:** **`ledgerWhere` (`invoices/domain.ts`) für jeden Leser von `Invoice`** (Angebote und Auftragsbestätigungen sind `docType` derselben Tabelle und gehören nie in Summen, Exporte, Berichte); **eine Stornologik** (`invoices.cancel`, Gegenbeleg mit Nummer). Die Schlussrechnung setzt Abschläge nach Entgelt und Steuer je Satz ab (§ 14 Abs. 5 UStG; Wortlaut = Steuerberater-Annahme), PDF und XML nennen dieselben Zahlen. Festgeschriebene Ausgangsrechnungen (`finalizedAt`) werden nie geändert oder gelöscht – jede neue Schreib-Operation prüft `isFinalized`. XML-E-Rechnungen liest ausschließlich `src/lib/einvoice` (kein DTD/keine Entitäten, linear). Die Hilfe nennt das Festschreiben nie „GoBD-konform“, steuerliche Aussagen nur als Hinweis. **Berichte** (`office/reports`) lesen nur über `ledgerWhere` plus das Quellrecht; `reports.export` in keiner Standardrolle.
* **PDF, Druck, Mail:** PDFs nur über `createPdf`/`pdfResponse` (`src/server/pdf`): die Rechteprüfung steht in der Route **vor** der Erzeugung, die Eingabegrenzen des Builders nie umgehen, kein PDF/A-3/ZUGFeRD (nicht nachweisbar; Rechnung als PDF + XRechnung-XML getrennt), QR über `lib/qr.ts` (UTF-8, Girocode). **Jede Funktion druckt ihre eigenen Daten** (eigene Route, kein zentrales `print`; Druckansicht `PrintLayout size`, Karten/Zettel ohne Preise). E-Mail nur über `queueMail` (`src/server/mail`, in der Transaktion): `mail.send` zusätzlich zum Fachrecht, Anhänge nur Dateien unter `files/` (begrenzt), Zielsperre, Versandlimits, Sendeprotokoll **ohne Inhalt**; die Empfängeradresse stammt fest vom Kunden/Beleg, nicht aus freier Eingabe.
* **Kalender-Abo** (`workshop/appointments/feed*.ts`): Token nur als Hash, identische 401 für alle Fehler, Feed nur mit `appointments.view` und aktiver Funktion, Abo-Adresse erlischt bei `revokeAccess` (Passwortwechsel, Deaktivierung, Notzugang, „überall abmelden“) und bei jeder Wiederherstellung; Abwesenheit nur als „abwesend“ (nie Art/Anmerkung).
* **Geld** immer als ganze Cent (`Int`, Obergrenze `MAX_MONEY_CENTS`), Eingabe über `parseMoneyToCents`. **Dateien/Bilder** liegen als normale Dateien unter `/data/files` (`src/server/files.ts`: `storeFile/removeFile/moveFile`, lesbare ASCII-Pfade, nie überschreiben, nie verändern – Backups nutzen Hardlinks); die DB hält nur den relativen `path`. Ausgeliefert nur über Route Handler mit Rechteprüfung. Nie Binärdaten in die DB.
* **Sensible Mitarbeiterdaten** (Notfallkontakt, Krankheit) nur mit `employees.sensitive`; Krankheit sonst maskiert (`visibleAbsenceType`), anderen Funktionen nur „abwesend“ (`userAbsentBetween`).
* **Fachliche Regeln:** Fahrzeuge (`Vehicle.customerId`) sind optional – nie `vehicle.customer.x` ohne Null-Prüfung, Anzeigename über `customerDisplayName()`. Nur die Doppelbelegung des Arbeitsplatzes ist hart; Feiertag, Öffnungszeiten, Abwesenheit, Kennzeichen-Dubletten sind Hinweise ohne Sperre. **Archiv statt Löschen** (Kunden, Fahrzeuge: `archivedAt`; Arbeitsplätze, Terminarten: `active`): Auswahlfelder, Suchen und Neu-Formulare blenden Archiviertes aus, Löschen nur, wenn nichts mehr daran hängt (`ArchivePanel` zeigt die Zählung); neue Tabellen mit Verknüpfungen: Archiv oder `Restrict`, nie stilles `Cascade` auf Historie. Feiertage berechnet nur `src/lib/holidays.ts`, gelesen über `getHolidays()`. Werkstattprofil (`getWorkshop()`): IBAN, USt-IdNr., Steuernummer nur über `lib/bank-tax.ts`; das Audit nennt nur Feldnamen. IT/Fuhrpark: Kosten pro Kilometer nur über den Kostenzeitraum (`costPeriod`); IP-Adressen je Subnetz eindeutig.
* **Übersetzungen:** `src/i18n/messages/de.ts` definiert die Struktur, `en.ts` muss identisch sein (Typfehler sonst). Größere Module haben `messages/modules/<modul>.de.ts` / `.en.ts` (`en` als `typeof de`). Dynamische Schlüssel über `td(key, fallback)`; Plural über `<key>_one` / `<key>_other` und `tp()`. **Anrede:** Oberfläche in der Nennform (kein „du“/„Sie“, `tone.test.ts`), Hilfe in der Sie-Form.
* **Dokumentation hat zwei Orte:** `README.md` = Entwicklerdokumentation (pflegen, wenn sich etwas Technisches ändert). `docs/` = Anwendungsdokumentation, in der App unter **Hilfe** (`/help`, kein Recht nötig): nur, was man **in der App** tut, keine Docker-/Entwicklerthemen. Kapitel einer Funktion liegen in `docs/<modul>/<funktion>.md` und werden von der Funktion in `help.ts` (`HelpTopicDef`) angemeldet (`src/modules/help.ts`); Allgemeines in `docs/platform/NN-name.md`. Ändert sich Bedienung/Verhalten, das Kapitel mitpflegen; neue Funktion = neues Kapitel samt `help.ts`.

### Oberfläche

* **UI-Bausteine statt eigener Elemente:** Buttons, Felder, Tabellen, Karten, Menüs usw. kommen **ausschließlich** aus `src/components/ui` (Liste README „Konventionen“; Listen sind `DataTable`, Zustände `StatusBadge` mit Ton aus `status-tone.ts`, Seitenkopf `PageHeader`, Aufklapper `Disclosure` auch `variant="card"`, Formulare `Form`/`FormActions`, Rückfragen `ConfirmDialog`, Einzelknöpfe `useInlineAction`). Für Belege/Aufträge/Zeit/Berichte (F0): `LineItemEditor`, `MoneyInput`, `Timeline`/`Stepper`, `ChecklistItem`, `StampButton` (Pflicht-Prop `actionId`), `SecretField`, `CodeBlock`, `Chart` (immer mit Tabellen-Alternative), `DateRange`, `PrintLayout`, `Signature`, `PhotoGallery`, `FileInput` (`multiple`, `variant="photo"`), `MarkdownScroll`, `Input masked`. Fehlt eine Variante, wird sie im Baustein ergänzt – nie lokal nachgebaut. Rohe `<button>/<input>/<select>/<textarea>/<table>/<label>/<details>` und die CSS-Klassen der Bausteine sind außerhalb von `components/ui` verboten (`ui-kit.test.ts`; die ALLOWLIST darf nur schrumpfen). Nur Funktionen dürfen für einen echten Spezialfall ein eigenes Element mitbringen, mit Kommentar `ui-kit-exception: <Grund>`.
* **Design:** nur Tokens aus `src/app/tokens.css` / Tailwind-Utilities (`bg-surface`, `text-ink-muted`, …), keine Rohfarben. Hell/Dunkel über `light-dark()`. **Touch:** Höhe von Bedienelementen und Eingabeschrift nur über `--tap`/`--tap-sm`/`--tap-chip`/`--tap-row`/`--input-font` (36 px/14 px am Desktop, 44 px/16 px bei grobem Zeiger und unter 1024 px) – keine festen `min-h-8/9`; eigene Links in Listen und Tabellen `min-h-(--tap-row) min-w-(--tap-row)`; Kennzeichen/FIN `autoCapitalize="characters" autoCorrect="off" spellCheck={false}`; `autoFocus` gilt nur am Desktop.
* **Mobil und Tablet** (README „Installierbare App (PWA)“, „Realgeräte-Checkliste“): Grid-Kinder mit breiten Inhalten tragen `min-w-0`; Unterlisten in einer Karte sind `DataTable bare`; Safe-Area über `env(safe-area-inset-*)`; lange Wörter brechen über `overflow-wrap`; Klebeleisten mit `glass-bar` statt `backdrop-blur`, **sticky nur ohne Überlauf-Vorfahren** (Wrapper `contents`, `--sticky-top`); Links in den UI-Bausteinen über `AppLink`. **Vor jedem Release** läuft die Realgeräte-Checkliste (iPhone, Android, iPad).
* **Installierbare App (PWA):** `public/sw.js` ist eine klassische Skriptdatei ohne Build und fasst nur Seitenaufrufe (bei **Netzfehler** die Offline-Seite `/offline`, die einzige Ausnahme von „keine Seitenantworten zwischenspeichern“) und `GET /_next/static/…` an. Alles unter `/api`, `Range`, Nicht-GET, `iframe`, fremde Herkünfte bleibt unberührt; **eine Download-/Dateiroute außerhalb von `/api` verlangt Anpassung von `classify` und `src/lib/sw.test.ts`**. Nie Cookies oder Antworten der Anwendung zwischenspeichern, kein `skipWaiting` ohne den Hinweis „Neue Version – Neu laden“; Abmelden leert die Zwischenspeicher. Manifest statisch ohne Datenbank (`src/lib/pwa.ts`), Symbole nur aus `scripts/gen-pwa-icons.mjs`; das Logo liefert `/api/logo` (öffentlich, **nur Raster, kein SVG**).
* **Datenaustausch (CSV)** (`src/server/csv`, `src/modules/exchange.ts`): Export und Import je Datenart mit **eigenen Rechten** (`<funktion>.export`/`.import`, gekennzeichnet, nie in Standardrollen/Token, keine API-Ressourcen). Der Import legt nur neu an (Dubletten überspringen, nie ändern), in **einer** Transaktion, mit Vorschau und Prüfsumme; Prüfung und Datensatz kommen aus den Operationen der Funktion. Texte des Nutzers gehen nur über `csvField` raus (Formelschutz); Zahlen des Programms als `Raw`/`moneyCell`.
* **React und Hilfe-Links:** `PageHeader help="…"` nur mit sichtbarem Kapitel. Kein `useEffect` mit synchronem `setState` (`react-hooks/set-state-in-effect`), keine `Date.now()`/`new Date()` im Komponenten-Rumpf (`react-hooks/purity`) – in Helfer auslagern.

### Tests und Prüfen

* **Tests:** Zeitmessungen prüfen Linearität statt fester Millisekunden (`measureLinearity`, `src/test/timing.ts`); Rechte-Änderungen an Operationen brechen `operation-permissions.test.ts` (Momentaufnahme: `UPDATE_OPERATION_SNAPSHOT=1`); im Browser-Test keine festen Wartezeiten (`page.clock`). Aktionen/Seiten mit dem Harness `src/test/harness.ts` gegen eine echte temporäre SQLite (Beispiele README „Tests“); der zu testende Code wird nach `createTestEnv()` per `await import()` geladen. Komponenten werden wirklich gerendert (`src/test/dom.ts`, happy-dom + react-dom/client), nicht per Quelltext-Muster geprüft. Matrix-Tests (`operations/matrix.test.ts`, `api/matrix.test.ts`) schalten ausgeschaltete Funktionen mit `enableDefaultOff` ein; Baumprüfungen nutzen `src/test/server-tree.ts`. **Zeilenenden sind LF** (`.gitattributes`, `src/line-endings.test.ts`).
* **Browser-CI** (`e2e/`, Playwright, nur Tests; README „Browser-CI“): Jede Funktion meldet ihre Seiten in `pages.ts` und `src/modules/pages.ts` (`pages.test.ts`); der Demo-Seed muss jede Seite abdecken; die Testseiten `/e2e-*` gibt es nur im Testmodus. Die **Baseline bekannter Verstöße ist leer** (`e2e/baselines/`): Verstöße werden im Code behoben, nie eingetragen; JS-Budget wächst nur mit `E2E_ALLOW_BASELINE_GROWTH=<Begründung>` (Log `growth.log`). Screenshots nur unter Linux/Docker und nur im eigenen Commit „snapshots“. Der Job `e2e` läuft nicht bei jedem Push auf `main`.
